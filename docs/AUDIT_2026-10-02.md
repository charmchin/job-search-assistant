- 单元配置验证：21 文件 / 561 用例、默认/危险继承环境隔离检查、类型检查和 lint 通过；补充验证锁文件的安全下限/明确版本、CLI 不回引、原静态 CSS 与许可。新增第五组真实 Chrome/API 回归，使用本机模拟 AI 验证已修复客户端、错误响应回退及人工确认；首次业务断言通过但旧清理脚本尝试取消 confirmed 草稿，被当前接口正确 409 拒绝，已改为只取消 pending 测试草稿，不放宽正式业务约束。所有测试禁用真实通知/钥匙串/文件操作，不消耗真实 AI 额度。
- 补充验收发现一次 macOS 进程清理 EPERM，独立取消诊断及原套件复跑通过，无残留。清理器现只在自身父进程已退出且系统快照确认组内无活动成员（空组或仅僵尸）时忽略该错误；有活动进程、快照失败或身份不明时仍报告权限失败。新增两例使用真实进程配合模拟 EPERM 验证两条分支，不通过全局吞错/重试掩盖失败。

## 结论

Next.js + SQLite + macOS LaunchAgent 的总体方案适合单人本地求职管理，不需要为了优化而重写技术栈。但当前存在能覆盖其他岗位信息、破坏恢复后数据可读性、绕过公开链接限制的缺陷，应优先修复。测试通过只能证明现有简单用例成立，尚不足以作为可靠性验收。

P1 表示优先修复的数据完整性或安全边界问题；P2 表示应在后续可靠性修复中处理的功能与防护问题。以下明确区分实测、模拟验证与静态审查。

## 1. [P1] 机会详情表单会串到其他岗位

位置：`components/opportunity-sheet.tsx:15–17`、`:41`；`components/workspace-app.tsx:61`。

浏览器实测：打开岗位甲，进入编辑，把组织名改为“岗位甲被编辑”，关闭详情，再打开岗位乙。乙的标题显示“乙工程师”，但公司编辑框显示“岗位甲被编辑”。点击保存后，乙的公司、岗位、备注被甲的内容覆盖。

原因：`OpportunitySheet` 在机会切换后保持同一个 React 组件实例；`form`、`edit` 等状态没有按机会 ID 重置。即使先保存甲，保留的 `form.notes`、`form.review` 仍可能在乙的备注页优先显示并被保存。

建议：按机会 ID 重建详情实例或显式初始化全部局部状态，关闭时清理；确保提交使用与表单绑定的机会 ID。未保存内容需要明确处理。

验收：编辑甲、取消或关闭、打开乙，乙的表单只能出现乙的数据；无论保存全部修改还是保存备注，都不能修改甲以外的记录。

## 2. [P1] 备份恢复会静默改写文本，也能提交不可读取的数据

位置：`app/api/import/route.ts:7–16`、`:20–36`。

隔离 API 实测：

- 普通备注 `2026-10-02T10:00:00+08:00` 导出并恢复后变成 `1790906400000.0`。
- 将备份中某机会的 `tags` 改为字符串 `not-json`，导入返回 HTTP 200 / `restored: true`；随后 `/api/state` 返回 HTTP 500，整个平台无法正常读取。

原因：备份仅校验各表为任意键值对象数组。`dbValue` 对所有 ISO 开头的字符串做日期转换，包括公司名、备注、正文等普通文本；JSON 数组、枚举、外键关系也没有逐字段校验。事务保证 SQL 错误回滚，但无法阻止逻辑无效的数据成功提交。导入成功前没有读回验证，也没有自动保存恢复前快照。

事务内部的 `foreign_keys = OFF/ON` 不会切换外键设置，已经使用内存 SQLite 验证。SQLite [官方说明](https://www.sqlite.org/pragma.html#pragma_foreign_keys)明确该设置在事务中不生效；这不是“外键已经关闭”的证据。

建议：为每张表制定严格备份 schema；只按字段名转换日期；固定允许的 SQL 列名；导入前验证关联关系、在临时数据库试恢复并读回；成功后再原子替换，保留恢复前备份。保持外键启用并使用固定写入顺序。

验收：完整导出再恢复，各字段逐一相同；无效日期、JSON、枚举、关联 ID 都在改写现有数据前拒绝；失败后原数据可读且内容不变。

## 3. [P1] 招聘抓取的私网限制可以绕过

位置：`lib/capture.ts:33–35`、`:68–82`。

模拟 fetch 验证（未实际访问内网）：`http://[::1]:3109/job` 与 IPv4 映射 IPv6 回环地址都通过了校验并进入 fetch。URL 的 IPv6 hostname 含方括号，与 `::1` 的字符串比较不一致。

静态审查：仅校验最初 URL 的 hostname 字符串，不解析 DNS 地址；`redirect: 'follow'` 不校验重定向目标。公开域名解析到内网、公开网站跳转到内网都没有被限制。网页抓取没有流式响应大小限制，`slice(0, 40_000)` 发生在完整下载和 HTML 解析之后。

影响：用户粘贴恶意或被控制的链接时，服务可能读取当前 Mac 可访问的本地/内网 HTTP 服务；若返回招聘式正文，内容可能进入草稿，配置 AI 时还可能被送往 AI 接口。超大页面可占用大量内存。

建议：统一解析 IPv4/IPv6；检查 DNS 解析后的地址并约束实际连接，逐跳检查重定向，限制跳转次数、端口与响应字节数。

验收：IPv6 回环、映射地址、DNS 私网解析、重定向至私网均被拒绝；过大响应在解析前终止；正常公开招聘页面可用。

## 4. [P2] AI 输出缺少运行时结构校验

位置：`lib/capture.ts:149–154`；`components/capture-dialog.tsx:43–46`。

模拟 AI 返回合法 JSON，但内容为 `tasks: "wrong-type"`、`highlights: null`、`deadline: "invalid-date"`、`confidence: 10`。`extractJob` 仍返回 `mode: ai`，保留所有无效值。TypeScript 的 `as Partial<Extraction>` 不会执行数据校验。

这些值随后进入 `tasks.map`、`items.map`、日期输入转换，可能导致草稿界面报错，不能按承诺自动回退到规则提取。

建议：用 Zod 校验完整提取结果、限制数组数量和文本长度、验证真实日期和置信度区间。失败时回退规则并告知用户。原文证据目前保存在数据库但草稿界面没有字段级显示，可一并补充。

验收：格式正确但结构错误的 AI 输出、数组 null、非法时间和超长内容都不会造成页面崩溃。

## 5. [P2] 提醒遗漏与终态节点处理不一致

位置：`lib/reminders.ts:17–32`。

隔离数据库固定时间验证：

- 已 `closed` 的岗位关联一个待处理面试节点，`checkReminders` 仍产生 1 条提醒候选。
- 服务关闭期间到期、已经过去 48 小时的独立任务，重启检查产生 0 条提醒候选。

原因：节点查询没有关联机会并检查放弃状态；所有候选只扫描最近 24 小时，没有记录上次扫描位置。后者使“重启汇总遗漏事项”只覆盖很短的停机情况。

提醒计算使用系统本地 `setHours/setDate`，与页面固定 Asia/Shanghai 的显示方式不完全一致。`nextActionAt` 没有进入提醒候选；任务仅到期时提醒；节点的自定义偏移可在创建 API 传入，但编辑 API 和界面没有完整配置入口。

建议：建立明确的时区与提醒策略；保存检查游标，重启只发送一条遗漏汇总；节点关联父机会判断是否仍有意义。Offer 后的体检、签约可保留，已放弃机会的节点应停止。增加通知测试按钮与可观察状态。

验收：跨 48 小时停机只产生一条汇总；已放弃节点不提醒；有效签约节点仍可提醒；固定时区和去重测试通过。

## 6. [P2] 今日排序会把临近截止的任务往后排

位置：`lib/domain.ts:26–34`；`components/workspace-views.tsx:16–20`。

固定时间实测：相同优先级、相同 72 小时组内，1 小时后到期且刚推进的任务 rank 为 `110000003600000`；2 天后到期但 12 天没推进的任务 rank 为 `109999136000000`，后者排在前者前面。

原因：把截止差与停滞时长相减，而不是依次比较字段；逾期任务的 `Math.max(0, delta)` 还会丢失实际截止顺序。风险雷达按机会更新时间排序；没有任务时，待判断机会也会先于临期机会成为焦点。

建议：使用明确 comparator：逾期/72 小时/7 天分组 → 优先级 → 实际截止时间 → 最后活动时间。把任务、节点、岗位截止和 `nextActionAt` 统一为可行动候选，说明推荐原因。

验收：同组同优先级下较早截止始终在前；停滞只作为后续比较条件；无任务的临期岗位也能成为焦点。

## 7. [P2] 本地 API 没有自己的跨来源防护

位置：`app/api/action/route.ts:17–19`、`app/api/import/route.ts:18–20`、`app/api/files/route.ts:10–19`。

隔离 HTTP 测试：带 `Origin: https://audit-untrusted.example`、`Sec-Fetch-Site: cross-site`、`Content-Type: text/plain` 的 JSON 创建请求被接受并写入数据。

浏览器测试：另一个真实本地 HTTP 来源（127.0.0.1 的不同端口）以 `no-cors` / `text/plain` 发起请求，成功创建隔离记录。模拟公网来源的 Chrome 测试被浏览器拦截，因此本次没有证明任意公网网站都能在默认 Chrome 上利用；浏览器的本地网络保护会影响利用条件。

原因：只监听回环地址限制了直接网络连接，但不替代 Origin/Host/请求类型校验；`request.json()` 可以解析 text/plain 请求。危险操作还包括整库恢复、AI 设置更改与打开任意存在的本机路径。

建议：统一验证允许的 Host 与 Origin，拒绝跨站写入，要求 JSON Content-Type；必要时使用本机会话随机 token。文件接口使用已登记材料 ID，拒绝应用程序或可执行文件等非材料目标。

验收：来自其他来源的写请求在执行业务前拒绝；本机正常页面和备份下载不受影响；无来源命令行检查按明确策略处理。

## 8. [P2] 保存失败通常没有界面反馈，基础更新校验不足

位置：`components/workspace-app.tsx:42`；`components/opportunity-sheet.tsx:17–22`；`components/workspace-views.tsx:82`；`app/api/action/route.ts:49–78`。

多个按钮使用 `void mutate(...)`，但 mutate 抛出的错误没有在这些操作入口捕获；保存失败可能仅成为 unhandled rejection。重复点击也没有通用提交锁。

隔离 API 实测：不存在的 task 更新返回 200；机会组织名可改为空；阶段可改为 `not-a-valid-stage`。创建与更新使用不同宽严标准，日期转换也没有显式有效性检查。

建议：共用字段 schema 与枚举；更新前检查记录存在；每次写入有 pending/success/error 状态，保留未保存内容并支持重试。写入成功但刷新失败时避免把写入当失败重复提交；关联活动记录的多步操作使用事务。

验收：服务不可用、非法输入、记录被删除、重复点击都有明确可见结果，不产生重复记录和静默成功。

## 9. [P2] 启动的提前返回会跳过更新检测

位置：`start.command:38–41`、`:74–84`；`scripts/macos-app.mjs:63–68`。

静态审查：只要 3000 端口的 `/api/state` 返回 2xx，就在检查迁移和源码更新时间之前退出；应用入口也有相同快捷返回。服务已经运行时修改代码，再点击启动入口仍打开旧构建。另一个服务恰好实现 `/api/state` 也可能被误认。

建议：增加带应用标识与构建版本的独立健康接口；明确“打开”和“更新/重启”流程；使用构建指纹并串行化迁移与构建。应用入口增加失败对话框，否则没有终端时启动错误不易看见。

目前 `.app` 的实际行为仍是打开默认浏览器，不是独立 WebView 窗口。Manifest 本身不会自动安装浏览器 Web App；原先设想的独立窗口、退出/备份菜单尚未实现。

验收：运行中的旧版本能被明确检测并更新；端口占用有可见错误；点击入口失败时无需手动寻找日志。

## 10. [P2] 自动测试缺少隔离，端到端命令不可用

位置：`vitest.config.ts:4–6`；`lib/capture.test.ts:2`；`lib/db.ts:8–16`；`package.json:15`。

现有 10 个单元测试通过，但 capture 测试导入模块时会初始化真实默认数据库，因为测试配置没有设置临时 `ZHAOPIN_DATA_DIR`。当前用例没有新增真实机会，但它们不是完全无副作用的纯单元测试。

`npm run test:e2e -- --list` 实际失败：Playwright 发现并加载 Vitest 文件，引发 `Cannot redefine property: Symbol($$jest-matchers-object)`，同时提示 `No tests found`。没有独立 Playwright 配置与有效端到端用例；本次浏览器复现是临时运行的审查脚本，不属于现有测试套件。

建议：测试初始化时强制临时库并禁用通知；分离 Vitest 与 Playwright 的目录和匹配规则，使用独立端口与库；把跨机会表单、备份往返、提醒固定时间和 API 拒绝场景加入回归测试。

## 依赖风险

本次 `npm audit` 报告 10 个包级告警：1 critical、3 high、6 moderate；`--omit=dev` 报告 6 个：1 critical、3 high、2 moderate。这个数量不等于可被当前应用利用的漏洞数量。

- 已安装 Next.js 16.3.3。官方 [GHSA-vcvr-r3jv-pc5j](https://github.com/vercel/next.js/security/advisories/GHSA-vcvr-r3jv-pc5j) 指出 Node.js ImageResponse 在特定不可信 SVG 输入下有远程代码执行风险，修复版为 16.3.6。当前业务代码未使用 `next/og` / `ImageResponse`，因此未发现该公告要求的利用路径；仍建议升级修复版本。
- undici 7.29.0 被报告存在多项告警，来自 cheerio 与 shadcn 依赖。应按实际抓取路径和上游兼容范围升级，不能把 WebSocket/特定 interceptor 的告警全部等同于当前 fetch 可利用问题。
- brace-expansion、fast-uri、hono、ip-address 告警主要随 shadcn 工具链引入。shadcn 是生成代码的 CLI，放在运行依赖中扩大安装面；可移到 devDependencies 或确认不再需要后去除。
- drizzle-kit 依赖旧 esbuild，属于开发工具风险。不要直接执行 `npm audit fix --force`；当前自动建议包含 drizzle-kit 的不合理大版本降级，应逐项评估。

以上风险信息来自当次 npm 审计和官方公告，依赖告警会随上游数据更新。

## 设计优化

1. 统一行动来源。现在 `nextAction`/`nextActionAt` 与 Task 相互独立，首页通常优先展示 Task，用户在草稿中填写的“下一步计划时间”没有进入完整提醒流程。可将下一步绑定实际 Task，保留手动指定焦点的能力。
2. 招聘历史应记录具体阶段变化及最高到达阶段。当前漏斗按当前阶段的线性序号推断所有前序步骤，例如进入面试会被推断参加过测评；跳过笔试、阶段回退都会让指标失真。失败与主动放弃合并，也限制了复盘解释能力。
3. 材料库缺少已录入材料的编辑、替换路径与删除入口；岗位材料要求主要在提取时建立，保存后新增要求也没有完整入口。文件被移动后当前界面无法顺畅修复引用。
4. 采用统一 schema + 按实体拆分的业务服务；当前 action 路由包含大量分支和多步写入，密集的一行式 JSX 增加状态与异常处理遗漏的可能。
5. 数据库结构目前维护在 Drizzle schema、SQL migration、运行时建表/ALTER 三处，应逐步收敛为单一迁移来源，避免再次发生兼容字段与迁移记录冲突。
6. `/api/state` 每次全量读取所有数据，并逐机会过滤任务、节点和活动，数量增长时会重复计算；可以先按机会 ID 分组，将历史活动与草稿分页。首页也需要窗口聚焦/适度轮询刷新，以更新跨天排序与停滞判断。
